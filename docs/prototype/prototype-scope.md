# 费用报销财务预审：模拟技术验证范围

> **MOCK / 模拟实验**：本文档中的规则、案例、材料摘要和审核结果均为虚构，不代表任何公司的真实制度或审核意见。

- **状态**：历史范围记录；文中 M1–M4 已实现为独立 Mock 实验，不代表当前业务页面的全部范围
- **新增时点**：财务 AI 场景初步梳理 V0.1 之后
- **工作线**：与财务访谈并行的“模拟技术验证”
- **设计输入**：`.specify/assessments/expense-reimbursement-precheck/intake.md` 与 `finance-interview-guide.md`

## 1. 为什么新增这条工作线

V0.1 和 intake 明确说明：真实审核步骤、公司制度、规则边界与人工权限尚未经财务人员通过真实案例确认。这一前提不变。

本实验不提前认定业务答案，只用完全虚构的数据和规则，提前验证一个很小的技术闭环是否能被清晰表达：

1. 接收一笔结构化报销信息和已生成的附件摘要。
2. 查找显式版本化的 `MOCK` 规则。
3. 识别材料缺失、材料冲突或无适用规则。
4. 输出可追溯的模拟结论，列出理由、证据来源、规则编号/版本与待人工处理原因。
5. 在没有匹配规则时停止自动判断，返回“规则待确认／人工复核”，不允许模型自行补造规则。

财务访谈负责发现真实业务；模拟技术验证负责检验最小契约与安全分支。两条工作线的结果不能相互替代。

## 2. 最小演示场景

只选择“`MOCK` 住宿费报销”，不扩展到交通、餐饮、招待、采购或其他费用类型。

本轮仅演示四种分支：

| 编号 | `MOCK` 情况 | 预期模拟结论 |
|---|---|---|
| M1 | 所需附件摘要存在，关键字段一致，且匹配到明确的 `MOCK` 规则 | `MOCK_PASS` / 满足模拟规则 |
| M2 | 缺少 `MOCK` 规则明确要求的材料摘要 | `MOCK_MISSING_EVIDENCE` / 缺材料，转人工补证 |
| M3 | 结构化报销信息与附件摘要之间出现显式矛盾 | `MOCK_REVIEW_CONFLICT` / 材料冲突，转人工复核 |
| M4 | 根据输入的适用范围未找到规则 | `MOCK_RULE_PENDING_REVIEW` / 规则待确认／人工复核 |

本轮不演示“超标自动驳回”或任何类似真实公司额度的阈值，避免把虚构数字误认为现行制度。

## 3. 目标

1. 固化一个足够小、可后续实现的输入输出契约。
2. 验证每个结论都能引用具体的输入字段或附件摘要，而不是只输出一段无法追溯的文本。
3. 验证规则必须具备显式编号、版本和适用范围，结论能记录实际匹配的规则快照。
4. 验证“缺材料”“材料冲突”“规则不存在”三种安全分支能明确转人工处理。
5. 为未来替换真实规则、真实材料和真实审核步骤预留明确接口，但本轮不执行该替换。

## 4. 明确不做的事

- 不设计完整财务 Agent，不设计自主规划、多 Agent 协作、长期记忆或自动放权。
- 不选型模型、OCR、RAG、Workflow 框架、数据库、消息队列或界面。
- 不读取真实发票、图片、PDF、付款凭证、员工信息或公司系统数据。
- 不接入任何报销、审批、财务、票验、支付或档案系统。
- 不将自然语言制度自动转换为可执行规则，不允许模型解释或补写缺失规则。
- 不检测发票真伪、重复报销、舞弊、异常消费或法律/税务合规性。
- 不自动通过、驳回、退回或修改任何真实报销单。
- 不把 `MOCK_PASS` 解读为财务审批通过；它只表示模拟输入满足模拟规则。
- 不修改 assessment 中的任何已知事实、待验证假设或访谈问题。

## 5. 这个实验能证明什么

在按后续设计实现并通过四个 `MOCK` 用例的前提下，它最多能证明：

- 设计的最小数据契约足以表达一类虚构住宿费检查。
- 在预先编码且版本化的模拟规则下，四种分支可以稳定、可重复地返回预期结构。
- 输出可以将结论、理由、证据、规则快照和人工处理原因分开记录。
- 没有匹配规则时，系统可以不生成替代规则，而是停止并转人工。
- 真实数据和真实流程将来可以通过明确的适配边界接入，而不必改变整个输出追溯结构。

## 6. 这个实验不能证明什么

- 不能证明模拟规则符合任何公司的报销、差旅、税务或会计制度。
- 不能证明 V0.1 中推演的五类审核对象、七环节判断链或四类输出符合财务实务。
- 不能证明附件摘要能从真实文件中准确、完整或安全地提取。
- 不能证明 AI 比规则引擎、流程优化、系统集成或人工审核更合适。
- 不能证明真实审核的准确率、召回率、节省时间、退回率或风险改善。
- 不能证明系统已满足隐私、数据安全、审计留痕、权限隔离、合规或生产可用性要求。
- 不能作为任何真实报销的审批、驳回、付款或问责依据。

## 7. 仍需财务确认的业务问题

本实验不回答以下问题，它们仍由财务访谈和真实材料核对完成：

1. 财务预审的真实起点、终点、责任人和与其他审批环节的边界是什么？
2. 住宿费报销实际需要哪些材料，不同组织、地区、人员、项目或场景是否不同？
3. 审核人员实际比对哪些字段，以什么顺序查看，如何处理缺失、冲突和例外？
4. 现行有效的制度、规则编号、版本、生效期、适用范围、所有者与更新机制是什么？
5. 哪些判断可以作为确定性规则，哪些需要上下文、经验或其他人的批准？
6. 真实审核结果、人工复核触发条件、升级路径和处理权限是什么？
7. 附件摘要在真实流程中能否使用，哪些判断必须回到原始凭证？
8. 真实材料的访问、脱敏、保密、存储、留痕和销毁要求是什么？
9. 如何用财务认可的脱敏样本与口径评估后续系统？

## 8. 未来替换真实内容的方式

| 本轮 `MOCK` 组件 | 未来替换来源 | 替换前的必要门槛 |
|---|---|---|
| 虚构结构化报销 | 经批准且脱敏的真实案例字段，或受控系统接口 | 财务确认字段含义与必需性；数据负责人批准用途、权限和脱敏方式 |
| 虚构附件摘要 | 真实凭证的受控解析结果 | 保留原始材料引用、文件指纹、页码/区域、提取方式与版本；完成准确性、隐私和安全评估 |
| `MOCK` 规则目录 | 经财务和制度所有者确认的规则快照 | 每条规则具备来源条款、编号、版本、生效期、适用范围、批准人与变更记录；不从模拟规则推导真实规则 |
| 固定的四分支顺序 | 财务人员通过真实案例演示出的审核步骤和分支 | 由实际审核人员核对；明确哪些是规则、哪些是人工判断、哪些不应自动化 |
| 虚构人工处理原因 | 真实复核、补证和升级机制 | 确认处理角色、时限、权限、留痕要求与异常处置路径 |

替换应是逐项、可回滚且可对比的：先固定一组经财务确认的脱敏案例作为回归集，再分别替换数据、材料摘要、规则和审核步骤。在财务未确认前，任何 `MOCK` 内容都不得去除 `MOCK` 标识或升级为真实规则。

## 9. 原设计完成标准与当前状态

- `mock-contract.md` 能表达四个 `MOCK` 用例，且所有结论都有结构化理由和证据引用。
- 无匹配规则时，契约要求返回“规则待确认／人工复核”，规则编号和版本保持为空，不生成伪规则。
- 文档对能证明与不能证明的内容有明确分界。
- 文档保留财务确认项，不将它们改写为技术假设或已知事实。
- 原设计要求先固定契约和范围，再创建实现。该门槛已经满足，M1–M4 已由独立 Mock 实验实现；这不扩大其业务真实性声明。
