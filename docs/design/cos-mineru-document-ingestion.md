# COS + MinerU 文档接入与解析设计说明书（供 Codex 执行）

## 1. 目标与前提

把现有“费用报销财务预审”工程中的文档入口接到腾讯云 COS 和 MinerU 在线精准解析 API，先跑通一张发票（PDF 或图片）：接收本地文件、内容去重、保存原件、提交解析、保存解析结果、查询结果。现有工程已经实现了部分能力，**先完整阅读工程并复用现有架构**，不要从零新建平行系统。

COS Bucket、Region、访问凭证和 MinerU Token 必须由部署环境提供，不在代码、公开文档或测试夹具中设置真实默认值。这里的 Bucket 是腾讯云 COS，不是阿里云 OSS。

第一阶段只做到“文档接入与原始解析结果”；发票字段标准化、业务规则、PASS/REVIEW 可沿用现有实现，但不要为了本任务重写或凭空补齐。保持主链路：接入 → 解析 → 标准化 → 校验 → 证据 → 决策 → 审计评测。

## 3. 职责与数据边界

| 层 | 输入与职责 | 持久化内容 |
| --- | --- | --- |
| 文档入口 | 接收文件、验证类型/大小、流式计算 SHA-256、查重 | 文档记录、原始文件的 COS object key |
| COS | 私有保存原件及解析工件，签发短期 GET URL | `raw/...`、`parsed/...`；不保存永久签名 URL |
| MinerU 适配器 | 提交 URL、取得 task_id、查询状态、下载结果 ZIP | 任务状态及非敏感诊断字段 |
| 解析工件 | 验证 ZIP，保留原始结果，提取入口所需文件 | 原始 ZIP、`full.md`、`content_list.json`，以及需要的其他原始文件 |
| 业务标准化 | 后续把解析结果转换为自己的 Invoice/Canonical Schema | 独立版本与证据引用，不直接把 MinerU JSON 当业务模型 |

外部查询可返回 `document_id`、`parse_run_id`、状态及成功后的 Markdown/内容列表入口；不返回 COS Secret、MinerU Token、持久化的预签名 URL。解析完成的返回物不是“MinerU 直接给一个发票 JSON”：在线精准接口返回 ZIP 地址，ZIP 内有 Markdown 和 JSON；字段业务 JSON 由后续标准化层生成。

## 4. 目标流程

1. **接收文件**：优先接到现有 API/CLI 入口；支持第一阶段实际要测的 PDF、PNG、JPEG。校验真实内容/扩展名、大小和空文件；上限按当前 MinerU 文档及工程配置执行。
2. **原件去重**：计算文件内容 SHA-256。若相同内容的完整文档记录及 COS 原件已存在，复用 `document_id`；不同文件名不能阻止去重。新文件用稳定且不会冲突的 object key 上传私有 COS，并写入文档元数据。数据库与 COS 不是同一事务，失败重试要可恢复，不能留下被误认为已上传的有效记录。
3. **解析去重**：用 `document_id + parser + 解析配置指纹` 查找成功的解析任务，命中则直接复用结果。已有 pending/running 任务时复用该任务并恢复查询，不重复提交。failed 任务允许显式重试并记录新尝试；显式 `force` 可产生新的 parse_run，用于重测。同一原件可以有多次不同配置的解析记录。
4. **提交任务**：服务端为 COS 私有对象生成临时 GET URL，验证 MinerU 从公网可直接 GET。签名有效期要覆盖排队到抓取文件所需时间，并可配置；若 URL 获取失败或过期，针对可识别的取件失败重新签发并重试，避免无条件重复提交。向 MinerU `/api/v4/extract/task` 提交，保存 `task_id` 后继续；传入稳定的业务 `data_id`（若适合现有模型）。不在日志里打印带签名的 URL。
5. **查询**：以项目现有后台任务机制为先；没有后台机制时用可恢复的服务层轮询/命令行，并给请求与整体任务设置超时、退避和有限重试。进程重启后能凭持久化 `task_id` 查询。区分 pending/running/converting/done/failed 以及本地下载/落盘失败；HTTP 成功还需检查业务 `code`。
6. **结果落盘**：MinerU done 后下载 `full_zip_url`，限制下载体积；安全检查 ZIP 成员路径与解压体积，保存原始 ZIP 到 COS，并验证/提取 `full.md` 与 `content_list.json`（必要时保留其余原始工件）。只有工件持久化成功且可读取，parse_run 才可标记为成功。以后查询从自己的存储取结果，不依赖 MinerU 临时结果链接。
7. **对外查询**：沿用现有风格暴露上传/发起解析/查询状态/读取结果；如果项目更适合一个 `ingest_and_parse` 操作，可以组合已有服务，但内部文档记录与解析运行仍独立。重复上传、重复解析明确返回 reused 状态，便于验证缓存命中。

## 5. 数据模型（概念模型，按现有结构适配）

`documents`: `id`, `sha256`（唯一）, `original_filename`, `media_type`, `size_bytes`, `cos_object_key`, `storage_status`, `created_at`。已有同义字段或表时复用，避免重复造表。原文件名仅作展示，不作为去重主键。

`parse_runs`: `id`, `document_id`, `parser`=`mineru`, `config_json`（规范化）, `config_fingerprint`, `task_id`, `status`, `result_zip_key`, `markdown_key`, `content_list_key`, `error_code`, `error_message`（脱敏）, `attempt`, `created_at`, `updated_at`, `completed_at`。同一个文档可有多个 run；为同配置正在运行/已成功的任务设计原子化查找或唯一约束，避免并发重复提交。`model_version` 等属于配置，不能把营销意义的 MinerU 版本号凭空填成实际模型版本；记录实际请求参数及服务端可观察版本。

配置指纹由影响输出的规范化参数生成，例如 model、OCR、语言、表格/公式、页码范围，以及适配器自身的配置版本。`force` 仅绕过本地缓存，不意味着删除旧 run。若后续字段抽取代码升级，只需重跑业务标准化；无需自动重跑 MinerU。

状态应明确区分 `queued/submitted/running/result_pending/succeeded/failed`（名称遵循现有工程），避免收到 MinerU 的 done 就提前宣布本地成功。保留失败原因和重试次数，但清除凭证与 URL 查询签名。

## 6. 第一版范围与验收

第一版采用 MinerU 在线精准 API + COS 预签名 URL；默认 `vlm`、`language=ch`、表格与公式开启。OCR 不凭扩展名绝对推断：图片可默认开启，PDF 默认按可配置参数处理，扫描 PDF 由调用方指定或后续识别。只支持单文件入口；不做批量、回调、独立任务队列、ES、向量库、LangGraph 或完整的财务预审流程，除非工程已经有成熟组件可直接复用。

验收应覆盖：

1. 一张有权使用的真实/脱敏发票经 COS → MinerU → 本地持久化结果完整跑通；确认返回 `document_id`、`parse_run_id`、状态、Markdown/JSON 工件的位置并人工抽查解析质量。
2. 同一文件改名再次提交，不重复上传；同配置再次解析不重新调用 MinerU；改变 OCR 或模型配置产生新的 run；失败可恢复或显式重试。
3. 凭证缺失、无效文件、COS 失败、MinerU 业务失败/超时、结果 ZIP 损坏或缺少预期内容均有可理解的错误，且不会错误标记为成功。
4. 运行仓库已有的相关测试，并为去重、状态转换、ZIP 安全边界写少量有意义的测试；外部服务用 mock/fake 覆盖。真实在线调用仅作为一次集成验收，需要凭证和测试发票齐备。
