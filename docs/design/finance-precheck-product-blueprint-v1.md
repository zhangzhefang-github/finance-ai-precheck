# 财务报销 AI 预审产品蓝图 V1

**用途：** 在开发页面前，对齐用户旅程、页面草图与现有能力。配套阅读《财务报销 AI 预审演示界面设计 V1》。
**依据：** 2026-10-04 已根据实际仓库、页面联调记录和 99 项离线回归测试更新。
**定位：** WSL2 本地单人 POC；预审报告，不是 OA 审批或付款系统。

## 一、用户旅程：一笔申请从进入到看懂结果

### 核心用户故事

> 作为演示者，我选择已有发票结果或上传一张新发票，独立填写申请金额和事由，发起预审。系统告诉我每一步的状态，并给出能对照原票、申请和来源证据的报告。遇到不确定或不一致时，它告诉我该由人核对什么，而不冒充正式审批决定。

| 步骤 | 用户动作与要回答的问题 | 页面反馈 | 后端与数据边界 | 异常去向 |
| --- | --- | --- | --- | --- |
| 0. 进入 | 想先看系统能做什么 | 默认显示已保存的报告列表和演示说明 | 只读 SQLite；不自动调用外部服务 | 无报告时展示样例使用指引，不伪造结果 |
| 1. 选入口 | 选“已有发票结果”或“上传新发票” | 明确标注已有结果无需 MinerU；新上传可能访问 COS/MinerU | 两条路径最后汇合到同一 extraction | 未有可信 extraction 时不能运行预审 |
| 2. 提交材料 | 上传 PDF/图片，或选择已有成功 extraction | 文件类型、大小和任务状态；显示可恢复的文档/解析 ID | 复用 `documents → parse_runs → invoice_extractions` | 上传、解析或加工失败，显示阶段和错误；不自动重提 |
| 3. 填申请 | 独立填写申请 ID、金额、币种、类别、事由 | 申请与发票提取字段并排预览，提示申请是 Mock | ClaimProvider 创建申请快照；不得从发票自动复制申请金额 | 申请 ID 和关联票据缺失时拒绝；金额、币种或事由留空时保存 `MISSING_EVIDENCE`；非空但格式错误时拒绝 |
| 4. 运行预审 | 明确点击一次“运行预审” | 处理中状态；展示是否走规则基线或模型 | 复用既有确定性检查、语义基线和受约束模型适配 | 模型超时/无效输出按既有语义进入 `REVIEW`，不自动重试 |
| 5. 看报告 | 看到了什么、为什么这个结果 | 原票、申请、提取字段、逐项检查、模型引用、来源链并排或分区展示 | 读取不可变 `precheck_runs` 与现有证据 | 原件暂不可读仍能看本地报告；明确证据可用性 |
| 6. 下一步 | `PASS` 是什么；`REVIEW` 查什么 | `PASS` 仅指 V1 已配置预审检查通过；`REVIEW` 显示待核对清单 | 不写回 OA、不审批、不付款 | 人工复核工作流待业务核对后另行设计 |

**成功路径：** 已有成功 extraction → 独立 Mock 申请 → 新报告 → 查看金额、服务语义和来源证据。
**异常路径：** 金额不一致/字段缺失/语义不明/模型错误 → 逐项解释并停在 `REVIEW` 或现有定义的相应状态。
**首次演示路径：** 先看已保存报告，再运行一笔 Mock 申请；只有明确要验证新文件时才触发 COS/MinerU。

## 二、页面草图：三屏与视觉重点

### 页面 A：报告列表（默认首页）

| 位置 | 元素 | 用户可做的事 |
| --- | --- | --- |
| 顶部 | 产品名“费用报销 AI 预审演示”、`PASS` 范围提示 | 识别系统定位 |
| 主区 | 报告行：生成时间、申请 ID、状态、金额差异、语义路由、模型是否调用 | 按报告 ID/状态筛选，打开详情 |
| 右上 | “新建预审”按钮 | 进入页面 B |
| 底部说明 | Mock 申请、真实票据、外部模型使用情况的来源标签 | 分清演示数据与真实工件 |

首页不展示“通过率”“准确率”等未经评测集支持的数字。

### 页面 B：新建预审

| 主区左侧：票据入口 | 主区右侧：独立申请 | 底部操作 |
| --- | --- | --- |
| 默认选择已有 `succeeded` extraction，显示类型、解析时间、脱敏摘要；或切换“上传新发票”，显示文件约束与处理阶段。 | 输入 `claim_id`、申请金额、币种、费用类别、申请事由；显示“Mock 申请，非 OA 数据”。金额不默认复制发票总额。 | 先校验输入，再展示提交摘要；“运行预审”只在明确点击时触发。新上传与运行预审分别确认，避免一个刷新触发两类外部调用。 |

新文件模式下，使用持久化任务 ID 展示 `原件上传 → MinerU 解析 → 工件保存 → 字段加工` 的真实状态。页面刷新后从数据库恢复；每个状态不是动画猜测。若解析耗时较长，页面提供手动刷新或安全轮询，不将 Streamlit 会话状态视为任务来源。

### 页面 C：预审报告详情

| 顶部结论条 | 左区：原票与来源 | 右区：事实与检查 |
| --- | --- | --- |
| 状态、报告 ID、生成时间、模型是否实际调用；紧跟范围说明。 | PDF/图片预览；选择字段后展示原文片段、页、块、表格行列和可用的 bbox 粒度。原件不可读时提示，不影响报告主体。 | 申请快照与发票字段先并排；下方按“材料、票面内部、金额、币种、语义”展示逐项检查、数值差异和原因。 |

底部折叠区提供 `document_id → parse_run_id → extraction_id → precheck_run_id`、schema/extractor/ruleset/prompt/model 版本、必要的技术错误码。规则基线判断必须显示 `route=baseline`；只有实际模型调用才展示其模型标识与两条逐字引用。整表 bbox 只能显示“来源表格区域”，不能圈成金额字段级坐标。

**阅读顺序：** 先结论与待核对项，再申请/发票事实，再证据与技术细节。不要让 COS key、ZIP 名称或 JSON 原文成为业务评审人的第一屏。

## 三、能力映射：页面要什么，现有链路有什么

下表已按当前仓库的实际服务、数据结构、页面行为和测试更新。仍未实现的能力直接列为缺口，不以目录名或设计意图代替实现事实。

| 页面能力 | 对应现有模块/数据 | 已知与缺口 | 最小接法 | 外部副作用 |
| --- | --- | --- | --- | --- |
| 列出报告 | `DemoQueryService.list_reports()`、`precheck_runs` | 已支持报告 ID、状态、人工反馈和异常筛选；当前是有上限的本地列表，不是正式分页 API | 页面复用只读查询服务和 SQLite 快照 | 无 |
| 查看报告详情 | `DemoQueryService.report_bundle()`、`precheck_runs`、证据与版本快照 | 已按保存时结果展示报告、证据、版本和追加反馈；UI 不重新计算业务结论 | 继续以不可变报告作为详情事实源 | 无 |
| 列出成功提取 | `DemoQueryService.list_extractions()`、`invoice_extractions` | 已只列出成功提取并提供创建预审所需摘要 | 页面选择器复用只读查询服务 | 无 |
| 查看原票 | `documents`、COS 原件 key、`CosObjectStorage.get_bytes()` | 可能需要凭证和有界预览；不能保证离线可见 | 只读、安全、有大小限制的预览；不可用则降级 | COS GET 可能发生 |
| 查看字段来源 | `invoice_extractions` 的证据 JSON | 页、块、表格行列与原文已存；字段级坐标未证明 | UI 如实显示证据粒度，不推断坐标 | 无 |
| 建立 Mock 申请并运行 | `DemoCommandService.run_precheck()`、`ExpensePrecheckService` | 已产生 `PASS / REVIEW / MISSING_EVIDENCE` 不可变报告；仍没有真实报销系统输入 | 表单形成独立申请快照并调用共享服务 | 仅在显式启用且基线无法判断时可能 AGICTO POST |
| 新文件上传与解析 | `DocumentIngestionService`、`documents`、`parse_runs` | 上传、提交、手动同步、失败与 `submission_unknown` 恢复链路已接入；长期 pending 的自动超时处置仍是缺口 | 页面复用原有 ingest/sync 和持久化任务 ID | COS 与 MinerU 调用 |
| 解析后结构化 | `InvoiceProcessingService.process()`、`invoice_extractions`、`invoice_checks` | 已在真实样本上完成解析后加工；当前仍是一申请关联一张发票 | 原服务加工，仅接受成功 parse run | COS GET 可能发生 |
| 人员角色/额度 | 当前未证实有可信 OA 或生效规则 | 不属于 V1 已实现判断 | 仅列未来接口，页面不宣称额度校验 | 无 |
| 人工复核动作 | `review_feedback`、Evaluation V1 的人工评价记录 | 已支持追加业务反馈及独立实验评价；仍没有正式审批、业务输入补正重跑关系或 OA 写回 | 保留追加证据语义，不把反馈覆盖为系统原结论 | 无 |

### 前后端联动契约的最低要求

每个页面操作约定：输入结构、输出结构、状态枚举、错误码、是否创建新记录、是否调用外部服务、重复点击/刷新语义、权限与来源标签。只读操作不得隐式迁移或写库；写操作有明确按钮与不可变新 ID。应用服务是共享边界，Streamlit 与 CLI 调同一服务；以后需要 React/OA 客户端时再把它包装成 FastAPI HTTP 路由与 OpenAPI 文档。

## 四、开发顺序与交付门槛

1. **仓库能力核对（已完成）**：实际服务、数据表、页面入口、外部副作用及测试边界已经盘点并写入本蓝图。
2. **只读切片（已完成）**：报告列表、筛选和详情复用已保存报告；断网仍可查看报告主体。
3. **提交切片（已完成）**：已有 extraction、独立 Mock 申请和新预审报告已在页面验收；真实模型只在显式配置且基线无法判断时调用。
4. **上传切片（核心链路已完成）**：COS/MinerU 上传、同步、加工和失败恢复已接入并验收；长期 pending 的超时与受控重试仍需后续处理。
5. **业务反馈与评测（部分完成）**：页面已支持追加业务反馈，Evaluation V1 已验证四类结果、补正重跑和规则变化比较；真实财务案例、真实制度和效果指标仍需业务验证。

**进入下一阶段的门槛：** 一个不了解代码的人能在页面上解释一笔 `PASS` 和一笔 `REVIEW` 的依据；页面行为与数据库报告一致；页面刷新不新增报告或外部任务；已知限制清楚标注。此后再判断是否需要 OA、额度规则、RAG 或异常调查 Agent。
