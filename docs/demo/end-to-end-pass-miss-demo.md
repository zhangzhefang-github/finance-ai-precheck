# 全流程演示用例：交通费 PASS 漏检与人工纠偏

## 1. 演示目标

用一个完全受控的 `MOCK` 用例展示：

```text
已解析票据
→ 独立填写申请
→ 运行预审
→ 查看 Check 与 Evidence
→ 人工发现 PASS 漏检
→ 追加业务反馈
→ 在 Evaluation V1 中记录范围内错误
```

这个用例专门展示系统的安全边界：系统可以保留原始判断，人工评价作为追加证据存在；人工反馈不会偷偷覆盖历史报告。

## 2. 用例故事

现有票据是一张客运交通服务发票，票面价税合计为 `181.73 CNY`。Mock 申请的金额、币种和费用类别都与票据匹配，但报销事由明确写着“本次未发生交通费用”。

当前关键词基线会因为“交通费用”与票面服务名称同类而输出 `SUPPORTED`，最终报告为 `PASS`。人工复核应识别其中的否定语义，把它记录为当前声明范围内的漏检，期望结果为 `REVIEW`。

这不是在演示真实制度违规，也不代表任何真实报销结论；它验证的是 PASS 漏检能否被发现、定位和留痕。

## 3. 启动页面

在仓库根目录执行：

```bash
set -a
source .env
set +a

.venv/bin/streamlit run prototype/streamlit_app.py \
  --server.address 127.0.0.1 \
  --server.port 8501 \
  --browser.gatherUsageStats false
```

浏览器打开 `http://localhost:8501`。

## 4. 第一段：确认已解析票据

进入侧边栏的“票据接入”。使用当前已经成功解析和加工的票据，不重新调用 COS/MinerU。

核对页面信息：

| 字段 | 预期值 |
|---|---|
| 票据类型 | 增值税电子普通发票 |
| 服务名称 | 运输服务 / 客运服务费 |
| 不含税金额 | `176.44` |
| 税额 | `5.29` |
| 价税合计 | `181.73` |
| 票内一致性 | `PASS` |

演示说明：票据解析结果已经持久化，页面刷新只读取本地状态，不会自动重新提交外部解析任务。

## 5. 第二段：创建 Mock 预审

进入“创建预审”，选择价税合计为 `181.73`、服务名称为客运服务费的已加工票据。

填写：

| 字段 | 输入值 |
|---|---|
| 申请编号 | `DEMO-NEGATION-20261013-001` |
| 申请金额 | `181.73` |
| 币种 | `CNY` |
| 费用类别 | `交通费` |
| 报销事由 | `本次未发生交通费用，请核对误填金额` |
| 判断方式 | `离线：只用版本化关键词基线` |

点击“运行预审并生成报告”。

## 6. 第三段：解释系统报告

当前实现的预期结果是：

| 项目 | 预期结果 |
|---|---|
| 申请完整性 | `PASS` |
| 票据证据 | `PASS` |
| 金额一致性 | `PASS` |
| 币种一致性 | `PASS` |
| 语义检查 | `PASS / SUPPORTED / route=baseline` |
| 最终状态 | `PASS` |

演示时应明确说明：这个 `PASS` 是当前实现的实际输出，但人工判断认为它有误。系统把“交通费用”这个同类关键词当成支持证据，没有识别“未发生”的否定语义。

在报告详情中依次展示：

1. 申请快照与发票快照互相独立。
2. 金额 Check 保存了申请金额、票面金额和差额。
3. 语义 Check 显示实际 route 和判断理由。
4. 报告保存 Evidence、输入指纹和版本信息。
5. `PASS` 只表示当前已配置检查通过，不代表正式批准。

## 7. 第四段：追加业务反馈

在报告详情底部的“人工复核”填写：

| 字段 | 输入值 |
|---|---|
| 复核结果 | `原预审判断有误` |
| 操作人标识 | `demo-finance-reviewer` |
| 复核备注 | `事由明确说明未发生交通费用，关键词基线漏掉了否定语义；该申请应进入人工复核。` |

点击“保存复核反馈”。

核对结果：

- 原报告仍然是 `PASS`。
- 页面新增一条人工反馈。
- 人工反馈没有覆盖原报告，也不被描述为正式审批。

## 8. 第五段：在 Evaluation V1 中记录漏检

进入“评测实验”。如果页面尚未加载内置案例，点击“初始化内置 Mock 案例”。

在“运行实验”中选择：

| 字段 | 选择值 |
|---|---|
| Case | `CASE-NEGATION · 关键词同类但事由明确否认发生` |
| Input Revision | `REV-NEGATION` |
| 执行策略 | `严格金额相等` |
| 父 Run | 首次运行不选 |
| 运行原因 | `首次运行` |

确认运行前摘要中的申请金额为 `181.73`，事由为“本次未发生交通费用，请核对误填金额”，然后点击“运行并保存”。预期 Evaluation Run 为 `COMPLETED`，报告状态为 `PASS`。

切换到“人工评价”，选择刚创建的 Run，填写：

| 字段 | 输入值 |
|---|---|
| 评价目标 | `某个 Check` |
| Check | `PRECHECK-SEMANTIC-001` |
| 人工判断 | `错误` |
| 问题类型 | `漏检` |
| 判断依据 | `Case 中的 Mock 预期` |
| Case 中的预期 | `对明确否认发生的事由，不应仅因类别词相同判定支持。` |
| 评价人标识 | `demo-finance-reviewer` |
| 期望结果 | `REVIEW` |
| 评价理由 | `申请事由明确否认费用发生，语义检查仍输出 SUPPORTED，属于当前声明范围内的 PASS 漏检。` |

点击“追加评价”。

核对结果：

- Evaluation Run 的原始 `PASS` 保持不变。
- 新增一条 `INCORRECT / IN_SCOPE / MISSED_ISSUE` 人工评价。
- 评价定位到 `PRECHECK-SEMANTIC-001`，而不是笼统修改整个 Case。
- 运行仍保留输入指纹、代码 commit、策略实现和报告快照。

## 9. 演示结论

建议用下面三句话收尾：

1. 系统能够把票据事实、申请事实、单项判断、Evidence 和最终报告分开保存。
2. 系统当前仍会出现可解释的语义漏检，因此人工复核和 PASS 反馈不能省略。
3. Evaluation V1 能保留原始错误行为、人工判断及具体错误位置，为后续修复和回归验证提供依据。

## 10. 可选扩展

如果还要展示“同一输入、不同规则行为”，继续使用内置 `CASE-AMOUNT / REV-AMOUNT`：先运行“严格金额相等”，再以第一条 Run 为父 Run 运行“MOCK 容差 0.05”，最后在“运行比较”中生成比较。固定输入为申请 `100.00`、票面 `100.03`，预期状态由 `REVIEW` 变为 `PASS`，变化维度为 `RULE`。
