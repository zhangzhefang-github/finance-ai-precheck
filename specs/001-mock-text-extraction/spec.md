# Feature Specification: MOCK 住宿材料文本字段提取实验

**Feature Branch**: Not created (no `before_specify` branch hook configured)

**Created**: 2026-09-23

**Status**: Draft

**Input**: User description: "在现有确定性 MOCK 费用预审原型前增加一个小型文本字段提取实验：从完全虚构的酒店发票摘要文本和付款摘要文本中提取金额、币种及适用的住宿日期，并生成现有契约需要的结构化附件摘要。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 提取清晰字段并追溯原文 (Priority: P1)

作为模拟实验审阅者，我希望从一段完全虚构的酒店发票摘要文本或付款摘要文本中获得金额、币种和适用住宿日期，并能从每个值回到输入文本中的原文证据。

**Why this priority**: 这是本功能的核心价值：先证明虚构文本可以转换为可核对的结构化摘要，而不是只产生无法追溯的答案。

**Independent Test**: 提交只含单一、明确金额、币种和住宿日期的 `MOCK` 文本，将提取值和证据引用与人工标注答案逐项比对。

**Acceptance Scenarios**:

1. **Given** 一段明确包含单一金额、币种和住宿起止日期的 `MOCK` 酒店发票摘要文本，**When** 进行字段提取，**Then** 每个目标字段都与人工标注值一致，且每个值都关联一段可在输入中精确定位的原文证据。
2. **Given** 一段明确包含单一金额与币种的 `MOCK` 付款摘要文本，**When** 进行字段提取，**Then** 金额和币种与标注答案一致并带原文证据；文本未明确表达的住宿日期不得从报销单或其他材料猜测。
3. **Given** 一份可无歧义提取的 `MOCK` 文本，**When** 生成现有契约的附件摘要，**Then** 金额使用两位小数字符串，币种和日期符合现有契约，且摘要保留 `MOCK` 标识。

---

### User Story 2 - 不确定时停止并等待人工 (Priority: P1)

作为模拟实验审阅者，我希望字段缺失、存在多个候选值或原文自相矛盾时，结果明确标记待人工确认，而不是自动选择、拼接或猜测一个值。

**Why this priority**: 不确定情况若被伪装成确定值，会让下游确定性规则在错误输入上产生看似可信的结论。

**Independent Test**: 分别提交缺少目标字段、包含多个无法排除的金额、包含互相矛盾住宿日期的 `MOCK` 文本，验证结果只报告不确定状态与候选证据，不产生自动选定值。

**Acceptance Scenarios**:

1. **Given** `MOCK` 文本未包含某个目标字段的可定位表达，**When** 进行提取，**Then** 该字段被标记为缺失且需人工确认，值保持为空，不得从报销单、规则或常识中补齐。
2. **Given** `MOCK` 文本中出现多个都可能是目标字段的金额，且仅根据原文无法唯一确定，**When** 进行提取，**Then** 金额被标记为多候选且需人工确认，所有候选值均保留各自的原文证据。
3. **Given** `MOCK` 文本对住宿起止日期给出两组互不相容的明确表述，**When** 进行提取，**Then** 相关日期被标记为冲突且需人工确认，两组原文证据均被保留。

---

### User Story 3 - 安全交付并中立比较 (Priority: P2)

作为现有 MOCK 预审原型的维护者，我希望文本提取仅产生现有契约需要的附件摘要，不改动报销单字段，不生成规则，也不绕过现有程序直接给出审核结论；同一批标注数据将来可以中立比较不同提取方法。

**Why this priority**: 保持“文本提取”与“规则匹配/结论”的责任边界，并避免在规格阶段预设确定性方法或模型方法更好。

**Independent Test**: 确认新输出仅位于附件摘要边界，不包含规则或审核结论；再用同一验收集和同一评分口径检查任意两份合规的提取输出。

**Acceptance Scenarios**:

1. **Given** 一份可无歧义提取的 `MOCK` 材料文本，**When** 生成附件摘要，**Then** 报销单字段保持原值，规则查找和最终结论仍由现有程序完成。
2. **Given** 现有 `MOCK-CASE-M1` 至 `MOCK-CASE-M4`，**When** 运行原有基线验证，**Then** 四个案例的结论、匹配规则和人工动作与新功能加入前一致。
3. **Given** 任意两种符合相同输出契约的提取方法，**When** 用同一验收集评估，**Then** 报告使用同一组指标展示结果，不预先宣布胜出方法。

### Edge Cases

- 文本为空、只有空白或仅有 `MOCK` 声明时，所有目标字段均不得猜测。
- 同一数值在文本中出现多次时，保留所有证据位置，不能因数值相同就忽略多候选可能性。
- 金额与币种分居不同文本片段时，若原文关系无法唯一确定，不得猜测关联。
- 文本同时包含付款日期、开票日期和住宿日期时，只能将原文明确标识为住宿/入住/离店的日期视为适用住宿日期。
- 只提供一个住宿日期、离店日早于入住日、或日期文字本身无效时，相关字段待人工确认，不自动修正。
- 酒店发票摘要与付款摘要之间金额或币种不一致时，提取层分别保留各文本中的值；是否构成审核冲突仍由现有程序判断。
- 任一输入、输出或案例缺少 `MOCK` 标识时，必须拒绝。

## Requirements *(mandatory)*

### Scope Boundaries

**In scope**:

- 单笔 `MOCK_LODGING` 场景的虚构酒店发票摘要文本与虚构付款摘要文本。
- 提取金额、币种、住宿开始日期和住宿结束日期，并保留字段状态、候选值和原文证据。
- 对可安全使用的结果生成现有 `attachment_summaries[]` 所需的结构化摘要。
- 用统一的虚构文本与人工标注答案评估提取结果。

**Out of scope**:

- 真实票据、付款材料、图片、PDF、OCR 结果或任何公司制度。
- 修改报销单自身的结构化字段。
- 创建、推测、解释或修改审核规则及规则版本。
- 直接给出任何审核结论。
- 选定模型、SDK、供应商、编程语言、类库、服务接口、存储系统或部署架构。
- 判定确定性方法或模型方法哪一种更好。
- 修改 assessment 文档或改写其中的事实与假设。

### Open Decisions

- **OD-001**: [NEEDS CLARIFICATION: 当任一必需字段缺失、多候选或冲突时，本轮是否应阻断整份附件摘要进入现有预审，还是允许输出部分摘要]
- **OD-002**: [NEEDS CLARIFICATION: 验收集的最小案例数以及清晰、缺失、多金额、日期冲突四类案例的分配是什么]
- **OD-003**: [NEEDS CLARIFICATION: 清晰案例的字段值/证据正确性阈值，以及不确定案例“不猜测、正确转人工”的必达阈值是什么]

### Functional Requirements

- **FR-001**: 系统 MUST 只接受显式标记 `data_classification = MOCK` 的文本输入、人工标注答案、提取输出和验收案例；缺少或不等于 `MOCK` 时必须拒绝。
- **FR-002**: 系统 MUST 区分 `MOCK_HOTEL_INVOICE_SUMMARY` 和 `MOCK_PAYMENT_SUMMARY` 两类输入文本，并保留可追溯的文本标识。
- **FR-003**: 系统 MUST 对金额、币种、住宿开始日期和住宿结束日期分别产生独立的字段提取结果。
- **FR-004**: 每个字段结果 MUST 包含状态、规范化值或空值、候选值列表、原文证据列表以及是否需人工确认。
- **FR-005**: 每个非空的提取值和候选值 MUST 至少引用一段与输入完全一致的原文片段，并提供可将其唯一定位到输入文本的开始和结束位置。
- **FR-006**: 系统 MUST 区分 `EXTRACTED`、`MISSING`、`AMBIGUOUS`、`CONFLICT` 和 `HUMAN_CONFIRMED` 五种字段状态。
- **FR-007**: 只有当原文提供唯一、无冲突且可追溯的值时，系统 MUST 将字段标记为 `EXTRACTED`。
- **FR-008**: 找不到可定位证据时，系统 MUST 输出 `MISSING`、空值和待人工确认标记，不得从报销单、规则、另一份材料或常识中补齐。
- **FR-009**: 出现多个无法唯一确定的候选值时，系统 MUST 输出 `AMBIGUOUS`、空值和待人工确认标记，并保留全部候选值及证据。
- **FR-010**: 原文对同一字段给出相互不相容的明确值时，系统 MUST 输出 `CONFLICT`、空值和待人工确认标记，并保留所有冲突值及证据。
- **FR-011**: 金额 MUST 规范化为现有契约要求的两位小数字符串，币种 MUST 规范化为验收集已标注的币种代码，且两者都必须保留未修改的原文证据。
- **FR-012**: 明确的住宿起止日期 MUST 规范化为 `YYYY-MM-DD`；付款日期、开票日期或其他日期不得冒充住宿日期。
- **FR-013**: 人工确认某字段后，系统 MUST 保留确认前的状态/候选值、确认值与关联证据，并标记为 `HUMAN_CONFIRMED`；本轮不设计人工操作界面。
- **FR-014**: 附件摘要与下游交付必须按 OD-001 的决策执行，且不得把未确认值伪装成现有契约的合法值。
- **FR-015**: 可交付的附件摘要 MUST 符合 `MOCK-CONTRACT-v0.1`，不得修改报销单自身的结构化字段。
- **FR-016**: 提取输出 MUST NOT 包含、生成或建议规则、规则编号/版本、合规性判断、审核理由或审核结论。
- **FR-017**: 现有程序 MUST 继续独立负责规则匹配、材料间一致性检查和最终 MOCK 结论。
- **FR-018**: 新功能加入后，现有四个 MOCK 案例的输入、结论、规则匹配和人工处理动作 MUST 保持不变。
- **FR-019**: 验收集 MUST 只包含完全虚构的 `MOCK` 文本与人工标注答案，并至少覆盖清晰提取、目标字段缺失、多个金额候选和住宿日期冲突；案例数与分布按 OD-002 决定。
- **FR-020**: 每个人工标注案例 MUST 包含期望字段状态、期望值或空值、所有应保留的候选值、对应原文证据与是否需人工确认。
- **FR-021**: 任意符合相同输出契约的提取方法 MUST 使用同一验收集和评分口径，分别报告字段值正确率、状态正确率、证据引用正确率和安全转人工率。
- **FR-022**: 本轮 MUST NOT 预设确定性方法或模型方法更好，也 MUST NOT 指定模型、SDK 或技术架构。
- **FR-023**: 验收阈值 MUST 按 OD-003 决定，所有参评方法必须使用相同阈值。

### Key Entities *(include if feature involves data)*

- **MOCK Material Text**: 一份完全虚构的酒店发票摘要文本或付款摘要文本；包含唯一标识、材料类型、`MOCK` 分类和原始文本。
- **Field Extraction Result**: 某个目标字段的结果；包含字段名、状态、规范化值、候选值、证据引用和人工处理标记。
- **Text Evidence**: 与输入原文完全一致的引用片段，以及该片段在原文中的开始和结束位置。
- **Extraction Candidate**: 一个可能的规范化值及其证据；一个字段可有零个、一个或多个候选。
- **Human Annotation**: 验收用人工标注答案；包含期望值、状态、候选、证据和人工处理标记。
- **Contract-Ready Attachment Summary**: 可交给现有 `MOCK-CONTRACT-v0.1` 的结构化附件摘要。
- **Evaluation Result**: 某种提取方法在固定验收集上的字段值、状态、证据与安全转人工指标。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 所有非空提取值和候选值均能通过原文片段和定位信息回到输入文本，可追溯覆盖率为 100%。
- **SC-002**: 对所有标注为缺失、多候选或冲突的字段，自动填入猜测规范化值的比例为 0%。
- **SC-003**: 清晰案例的字段值、状态和证据引用，以及不确定案例的安全转人工行为，达到 OD-003 决定的阈值。
- **SC-004**: 审阅人员在 30 秒内能借助任一字段的证据引用找到对应原文，在验收集上的完成率为 100%。
- **SC-005**: 任一参评方法均能在同一验收集上报告字段值正确率、状态正确率、证据引用正确率和安全转人工率四项可比指标。
- **SC-006**: 新功能加入后，现有四个 MOCK 案例全部保持原有结论，回归一致率为 100%。
- **SC-007**: 验收集、输入、提取输出和附件摘要的 `MOCK` 标识覆盖率为 100%，非 MOCK 输入的拒绝率为 100%。
- **SC-008**: 全部验收输出中，提取层包含审核规则、规则版本或审核结论的比例为 0%。

## Assumptions

- 本功能位于现有确定性预审基线之前，只向下游交付结构化附件摘要。
- 报销单自身的结构化字段保持原样，不作为文本提取缺失值的候选来源。
- “适用住宿日期”仅指原文明确表达为住宿、入住或离店的日期；付款日期或开票日期不作为替代值。
- 原文证据由完全一致的引用片段和半开区间字符位置 `[start, end)` 组成，索引以未修改的输入文本为准。
- 验收集由人工编写和标注，不从真实票据、公司制度或生产数据改写而来。
- 人工标注答案在评估期间作为唯一验收基准；若标注存在歧义，先修正标注。
- 方法比较仅在参与方法能提供相同契约输出时进行；本轮不要求同时实现确定性方法和模型方法。
- 人工确认会以结构化记录表示，但本轮不设计人工处理界面、权限或工作流。
